# 实施思路与完整性保障

## 一、总体策略

不照设计文档一次性重写，而是把它作为目标架构，通过并行建设、自动对账和灰度切换逐步落地：

```text
固定旧系统基线
→ 建 V2 并行库
→ 清洗并迁移数据
→ 建 /api/v2
→ 新旧双读对账
→ 前端按模块切换
→ 灰度发布
→ 旧库只读保留
```

不直接修改旧表，不在第一天让前端切到新库。完整性不是口头保证，而是每个阶段都有可量化的通过门槛。

## 二、阶段 0：保护现场

1. 记录 `git status`，区分用户已有改动和本次改动。
2. 建立独立实施分支，不覆盖当前工作区中的未提交内容。
3. 对现有数据库执行 `pg_dump`。
4. 给桌面 CSV、SQL、原始文件计算 SHA-256。
5. 保存现有 API 的典型输入输出。
6. 轮换已经出现在仓库或前端中的数据库密码和 Dify Key；交接文档不得记录真实密钥。
7. 建立至少 100 条真实业务问题及人工确认答案，作为黄金测试集。

此阶段只建立可恢复基线，不修改旧数据。

## 三、阶段 1：建立工程骨架

建议把数据库实现从桌面和零散文档迁回仓库：

```text
db/
  migrations/
  seeds/
  staging/
  tests/
api/
  app/
  tests/
worker/
infra/
  compose.yaml
docs/
  architecture/
```

为了降低迁移成本，可保留 FastAPI，但替换当前手写连接池，采用 FastAPI、SQLAlchemy 2、Alembic、psycopg pool、pytest/Testcontainers。Taro 前端不重写。

每项数据库变更必须成为不可修改的 migration。Schema migration 与 data migration 分离，生产环境以向前修复 migration 为主，不编辑已经执行过的文件。

## 四、阶段 2：V2 数据库并行建设

V2 使用独立 schema，不修改旧表：

```text
iam → core → knowledge → policy → content
    → assessment → generation → analytics
    → ingestion → audit
```

建设顺序：

1. 组织、权限、知识集合。
2. 证书、别名、科目。
3. 资产、版本、片段。
4. 知识点和知识关系。
5. 政策版本、条款、事实和证据。
6. 教材、章节。
7. 试卷、题目。
8. AI 生成、引用和审核。
9. 导入批次和审计。

阶段门槛：

- 空数据库可由 migration 一键构建；
- 已存在数据库可从上一版本升级；
- FK、唯一键、CHECK 都有成功和失败测试；
- 所有外键列具备合适索引；
- migration 状态与实际 schema 无漂移。

## 五、阶段 3：Staging 与数据迁移

不得把现有 CSV 直接导入正式表：

```text
CSV
→ staging 原始表
→ 格式校验
→ 重复和引用校验
→ 业务规则校验
→ validation_error
→ 全批通过后单事务提交
```

### 必须生成的迁移证据

#### 1. ID 映射报告

```text
旧 cert_id → 新 certificate.code → 新 bigint id
```

#### 2. 数据对账报告

逐表记录原始行数、成功迁移数、拒绝数、合并数、重复数、缺失引用数、空值覆盖率和内容哈希。必须满足：

```text
旧记录数 = 已迁移 + 明确拒绝 + 明确合并
```

不能出现来源不明的数据损失。

#### 3. 待业务确认清单

包括错误别名、证书歧义、无政策依据的事实、无法确认时效的政策、私有资料版权和保密级别。不确定数据进入 draft，不由实施模型自行猜测修正。

## 六、阶段 4：API V2 并行建设

保留旧 `/query/*`，并行创建：

```text
/api/v2/certificates
/api/v2/exam-events
/api/v2/eligibility/evaluate
/api/v2/knowledge/search
/api/v2/generations
/api/v2/admin/assets
```

API 必须实现：

- 身份认证和 collection ACL；
- 政策有效期、published 和 approved 过滤；
- 结构化报考判断；
- 每项政策结论返回资产版本和片段引用；
- restricted 数据在检索前鉴权；
- 数据库故障返回 5xx，禁止伪装为空数据；
- Dify Key 只在后端；
- 生成任务记录模型、prompt 版本、输入片段、引用和输出版本。

## 七、阶段 5：新旧双读对账

同一个请求同时查询旧系统和 V2，但用户仍使用旧结果：

```text
请求
├─ 旧 API → old_result → 用户
└─ V2 API → new_result → comparison
```

比较证书解析、报考判断、考试日期、合格线、政策版本和引用。差异进入 comparison 报告，经业务人员确认后才能进入切换清单。

## 八、阶段 6：前端逐模块切换

按风险从低到高切换：

1. 证书下拉；
2. 考试日程；
3. 报考和政策查询；
4. 知识检索；
5. 内容生成；
6. 审核和引用展示。

每个模块使用独立 feature flag：

```text
USE_CERTIFICATE_API_V2
USE_ELIGIBILITY_API_V2
USE_GENERATION_API_V2
```

单个模块失败时可单独切回旧 API。前端需要删除硬编码 Dify Key，增加统一 httpClient，并把生成流程改成后端任务 + SSE。政策数字缺少引用时，审核界面不得允许通过。

## 九、完整性验证矩阵

| 维度 | 验证方式 |
|---|---|
| 代码完整性 | 独立分支、小提交、diff 审核、build、typecheck、lint、测试 |
| Schema 完整性 | 空库重建、版本升级、约束测试、schema diff |
| 数据完整性 | 行数、哈希、FK、唯一键、空值、ID 映射和拒绝清单 |
| 业务完整性 | 100 条黄金问题，新旧结果和人工答案比较 |
| 引用完整性 | published 事实必须 approved 且有 primary evidence |
| 权限完整性 | restricted 越权检索、下载和生成泄漏率为 0 |
| AI 完整性 | 记录模型、prompt、输入片段、引用和输出版本 |
| 运维完整性 | 备份恢复、迁移失败、服务降级和 API 回滚演练 |
| 前端完整性 | H5 构建、关键流程 E2E、feature flag 回退 |

## 十、发布门槛

至少满足：

- H5 build、TypeScript typecheck、lint 通过；
- migration 和数据库约束测试通过；
- API 单元、集成和权限测试通过；
- valid CSV 全部导入；invalid CSV 全部命中预期错误码；
- 结构化报考判断准确率不低于 99%；
- 政策引用正确率不低于 98%；
- restricted 越权泄漏率为 0；
- 备份恢复演练成功；
- 业务负责人确认数据差异清单。

任一 P0 门槛失败，不得标记为完成或切换生产流量。

## 十一、回滚策略

- 前端通过 feature flag 切回旧 API；
- V2 停止接收写入但不删除；
- 旧数据库保持只读并保留至少两个发布周期；
- 已执行 migration 不修改，通过新的前向 migration 修复；
- 对象存储版本、导入批次和审计记录不删除；
- 只有完成恢复演练和业务验收后才退役旧库。

## 十二、与“直接制作型 Agent”的区别

直接制作型 Agent 可能优先生成所有表、API 和前端代码；本方案优先建立基线、约束测试、数据对账、权限边界和回退路径，再逐块实现。速度可能稍慢，但不会把数据迁移、权限和业务正确性留到上线前补救。

实施 Agent 应先提交计划、风险清单、业务待确认项和第一批测试，再开始大规模修改。
