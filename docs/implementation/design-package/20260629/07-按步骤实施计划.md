# 按步骤实施计划

## 0. 计划目标

本计划用于在不破坏当前 Taro 项目、不丢失现有数据库和私有资料的前提下，逐步实施企业知识资产平台 V2。

核心约束：

1. 一次会话只执行一个工作包。
2. 每个工作包必须以“验证通过 + 状态更新 + 独立提交”结束。
3. 额度不足时不得开启下一个工作包。
4. 禁止留下未执行完的 migration、半切换 API 或无法构建的前端。
5. 每个工作包可以单独回滚或通过 feature flag 禁用。

## 1. 当前项目基线

已知项目情况：

- 前端是 Taro 4 + React + TypeScript；
- 已有 `build:h5`、`typecheck`、`lint` 脚本；
- 当前证书列表通过 `src/services/policyApi.ts` 调用 8400 端口；
- `src/services/dify.ts` 由浏览器直接调用 Dify，且存在需轮换的前端密钥；
- FastAPI/pg8000 数据库桥接代码仍放在 `docs/dify/v3/policy_api.py`；
- 仓库没有正式 migration、数据库测试、后端工程和 compose；
- 当前工作区已有其他未提交修改，实施 Agent 必须保护这些修改。

没有可以直接复用的后端分层和测试模式。实施时需建立新模式，但不得假装仓库已有约定。

## 2. 防止“做一半”的执行协议

### 2.1 固定状态文件

第一包创建：

```text
docs/implementation/IMPLEMENTATION_STATUS.md
docs/implementation/DECISIONS.md
docs/implementation/DATA_ISSUES.md
docs/implementation/NEXT_TASK.md
```

`IMPLEMENTATION_STATUS.md` 记录：

```markdown
| 包 | 状态 | Commit | 验证 | 阻塞 |
|---|---|---|---|---|
| WP00 | completed | abc123 | PASS | - |
| WP01 | in_progress | - | - | - |
```

状态只能是 `pending/in_progress/completed/blocked`。

### 2.2 每轮开始协议

1. 读取交接包全部文件。
2. 读取 `IMPLEMENTATION_STATUS.md` 和 `NEXT_TASK.md`。
3. 执行 `git status --short`，不得覆盖非本包修改。
4. 只选择编号最小且依赖已完成的 pending 工作包。
5. 在状态文件中把该包改为 in_progress。
6. 先写或确认测试，再修改实现。

### 2.3 每轮结束协议

1. 运行该包的全部验证命令。
2. 检查 diff，排除缓存、密钥、临时文件和无关修改。
3. 更新状态、数据问题和决策记录。
4. 写清下一包的唯一入口任务。
5. 创建一个独立 commit。
6. 到此停止，不顺手开启下一包。

### 2.4 Context/Token 边界

以下节点适合手动 compact 或开启新会话：

- WP00 完成后；
- 每两个数据库工作包之后；
- 数据迁移完成、API 开始之前；
- API 完成、前端切换之前；
- 双读分析结束、生产切换之前。

禁止在 migration、数据回填、API 半切换或测试失败时 compact。

| 风险 | 处理方式 | 是否阻断 |
|---|---|---|
| 当前工作区有用户未提交修改 | 独立分支/工作树，避免覆盖 | 是 |

## 8. 实施 Agent 的首次动作

实施 Agent 不应马上创建几十张表。第一次只执行 WP00，并在提交前向用户报告：

1. 当前工作区哪些变更不是本项目迁移产生的；
2. 备份是否完成并可读取；
3. 三个原始资料位置及哈希清单；
4. 当前 build/typecheck/lint 基线；
5. 发现的真实密钥仅报告位置和轮换状态，不展示值；
6. WP01 是否具备开始条件。

收到用户确认后，再开始 WP01。
